# X 判定 v2：文风通道（C / D）与多通道组合器

- 上游主计划（Phase 1–5 已全部完成）：[2026-07-24-x-source-local-probe.md](2026-07-24-x-source-local-probe.md)

## 1. 一句话背景

单通道 dense kNN（通道 B）已上线并于 2026-07-27 用真实标注回测完毕：**正判定可用（100% 精确），
负判定不可用（等同瞎猜），已默认关闭**。本计划要做的是让判负重新成为可能——不是调阈值，而是
补上能表示「文风」的通道。

## 2. 为什么判负失效（这一节决定了后面所有设计，别跳过）

回测事实（59 个标注，留一法，生产库快照）：

| 侧 | 最好一档 | 精确度 | 基率 | 结论 |
|---|---|---|---|---|
| 正 | D0.60 / M3 / `>=0.25` | **100%**（8 次） | 50.8% | 有真实信息，已上线 |
| 负 | 整个网格最好的一格 | **55.6%** | 49.2% | 没有信息，已关闭 |

按踩的理由拆召回（D0.60 / M3 / −0.45）：

| reason | 个数 | 被召回为 negative |
|---|---|---|
| `promo` | 11 | 2 |
| `engagement_farming` | 10 | 0 |
| `ai_slop` | 3 | 0 |
| `author` | 1 | 0 |
| `topic` | **1** | 0 |
| （无理由，chips 之前） | 3 | 0 |

**根因**：embedding 是按语义/话题训练的，向量编码「这条推在讲什么」。而 24/29 的踩说的是
「这条推怎么说话 / 谁说的」。于是「我讨厌这种腔调」被记成了「我讨厌这个话题」，双向都坏——
换个话题的同款营销推漏网，而你点过赞的、恰好同话题的推被判负（回测里 3 次错误判负全是这种）。

**推论（本计划的立论）**：判负要复活，需要一个**表示层能承载文风属性**的通道。这不是调参能到达
的地方；反过来，正判定不需要新通道，因为点赞的动机本来就是话题性的，和 embedding 对齐。

**副推论（数据侧的免费修复，值得同时做）**：如果用户开始多按「不感兴趣」（`topic`），通道 B 的
负向会自行恢复。所以 B 的负样本训练集将来应当**只取 `reason IS NULL OR reason='topic'`**——今天
这么做不行（只剩 4 个负样本），等 `topic` 踩攒到几十个再切。见 §7 的开关设计。

## 3. 现状清单（接手前先确认这些还成立）

代码与常量（`condenser/`）：

| 位置 | 现状 |
|---|---|
| `verdict.py` | `run_once` = 丢弃撤销 → 冷启动闸门 → 补索引 → 判定 → 清理；`score_neighbours` 是唯一打分点，负分支已被 `condenser_verdict_negative_enabled` 拦住 |
| `vectors.py` | sqlite-vec 封装（`x_vec_labeled` vec0 表），扩展不可用时全部 no-op |

| `config.py` | `positive_score=0.25`（回测定案）、`negative_enabled=False`、`max_distance=0.6`、`min_neighbors=3`、`k=15`、`min_down_neighbors=2`、冷启动 20/20、`window_hours=48`、`batch=100` |
| `db.py` | `x_labeled_samples()` = `item_feedback`(source='x') ∪ `saved_items`(source='x')，实时读表；`FEEDBACK_REASONS` = topic / promo / ai_slop / author / engagement_farming |
| schema | v9。`x_tweets` / `x_feed_items`(verdict, verdict_meta) / `x_embeddings` / `x_vec_labeled` / `item_feedback`(verdict, reason) |

生产数据（2026-07-27 晚）：标注 30 👍 / 29 👎 / 0 收藏；For You 存档 ~147 条；判定 17 正 /
71 中性 / 0 负；probe 每小时 20 条（`CONDENSER_X_HOME_COUNT=20`），只在 Mac 醒着时跑，
实际约 300–400 条/天。

⚠️ **数据量是本计划的前置条件**：通道 C/D 是统计模型，59 个标注喂不动。笔记给的量级是
**百到千**。按现在每天标 20~30 个的节奏，4~6 周能到几百。**可以先写代码、先攒属性数据，
但不要在几十个标注上宣布任何通道「有效」或「无效」**——那正是这次回测能做出结论的原因：
它做在一个已经能明确分出胜负的对比上（100% vs 基率）。

## 4. 目标架构（来自笔记，本计划落实其中的 C / D / 组合器）

```
新 For You 推文
   ├─ A 作者先验     （该作者的 up/down 计数，Beta 平滑）   ← 低优先，只有 1 个 author 踩
   ├─ B 话题 kNN     （已上线；正向可用，负向待 §7 的 reason 过滤后再议）
   ├─ C 属性通道     （LLM 抽 topics + style_flags，逐属性贝叶斯计分）  ← 第一优先
   └─ D 词面通道     （n-gram 贝叶斯，垃圾过滤血统）                    ← 第二优先
                     ↓
              组合器（v1 手调加权和 → 数据够后逻辑回归 stack）
                     ↓
        既有闸门体系原样保留：证据不足→neutral、不对称阈值、verdict_meta 可解释
```

**每个通道必须独立可关、独立可回测**——这是笔记的核心要求，也是这次能干脆关掉 B 的负向的原因。

## 5. 通道 C：LLM 属性抽取（第一优先）

### 5.1 为什么是它

24/29 的踩是文风判断，C 是唯一直接表示文风的通道。LLM 在这里**不是裁判，是特征工**：
只吐属性，不吐判断。判断仍由贝叶斯计分 + 既有闸门做出——这保证了可解释性和「标注越多越准」
的性质，也避免了「每轮 LLM judge」的成本与不可复现。

### 5.2 数据模型（schema v10，纯新增表，无迁移）

```sql
CREATE TABLE x_attributes (
    tweet_id     INTEGER PRIMARY KEY,     -- 与 x_tweets 同键
    topics       TEXT NOT NULL,           -- JSON 数组
    style_flags  TEXT NOT NULL,           -- JSON 数组，取值来自封闭 taxonomy
    model        TEXT NOT NULL,           -- 'qwen-flash@v1'：模型@taxonomy 版本
    created_at   TIMESTAMP NOT NULL
);
CREATE INDEX x_attributes_model ON x_attributes(model);
```

设计要点：

- **和 `x_embeddings` 同性质：可重建的缓存**。原文在 `x_tweets` 里，任何行都能重抽。
- `model` 字段编码 **模型 + taxonomy 版本**。taxonomy 改了 = 旧属性不可比 = 重抽而不是迁移
  （完全照抄 `embedding.model_tag` 的 `name@dims` 约定，理由相同）。
- **不做属性到标签的物化表**。计分时实时读 `item_feedback` ∪ `saved_items` 做计数——和 B 的
  训练集「实时读表」保持一致，取消标注即自动退出，无需同步代码。

### 5.3 taxonomy（先手写，别让 LLM 自由发挥）

`condenser/attributes.py` 里一个常量，**封闭集合**，非法值丢弃并计数。初版 style flags 建议
从已有的 reason chips 长出来（它们是用户亲口说过的四种毛病），再补笔记里点过名的几种：

```
promo_cta          广告/推销，带行动号召
engagement_bait    钓互动：hook + FOMO + 「save this 🔖」+ 正文钓在评论区
thread_bait        🧵 1/N 长贴钓关注
ai_slop            AI 生成腔（模板化排比、空洞总结、emoji 小标题）
listicle           「5 个你必须知道的…」
emoji_spam         emoji 轰炸
humblebrag         凡尔赛 / 成功学
outrage            愤怒钓（rage bait）
poll_bait / giveaway / crypto_shill / dropshipping ...
```

topics 用开放短语（`['llm', 'rust', '创业']`），不封闭——话题空间本来就长尾，而且 B 通道已经
覆盖了话题，C 的 topics 主要用于 `verdict_meta` 的可解释性和将来的组合器特征。

⚠️ **chips 是 C 的监督信号**：`item_feedback.reason` 直接对应 style flag（`promo`→`promo_cta`，
`ai_slop`→`ai_slop`，`engagement_farming`→`engagement_bait`/`thread_bait`，`author`→通道 A）。
一条「踩 + 广告营销」的标注说的是「**这条推的 promo 属性**该被记负分」，而不是「这条推整体
该被记负分」——这正是笔记里 credit assignment 的正身，也是 chips 当初存在的理由。计分时应当
优先按 reason 定向记账，无 reason 的踩退化为「给该推所有 style flags 平摊」。

### 5.4 抽取管线

- 新模块 `condenser/attributes.py`，结构对照 `embedding.py`：OpenAI 兼容、`CONDENSER_ATTR_*`
  配置（base_url / api_key / model / batch / enabled）、`available(settings)` 无 key 即整条通道
  inert、批量 + 重试 + 结构化输出（JSON schema / function calling，解析失败按「无属性」丢弃并计数）。
- 触发点与 embedding 完全一致：`verdict.run_once` 里，**在冷启动闸门之后**（闸门关着不花钱），
  对「窗口内未判定的 For You 推文」+「所有已标注推文（补齐历史）」抽属性。
- **成本估算先算再写**：~400 条/天 × （推文 ~100 tok + 输出 ~50 tok）。选便宜模型（qwen-flash /
  haiku 级别）时约等于噪声；但**必须有 `CONDENSER_ATTR_BATCH` 上限和 `enabled` 开关**，
  并把当轮抽取数写进日志与 `/api/x/status`，否则这是本项目第一个「按条计费且无上限」的组件。
- **先补齐已标注的 59 条**（一次性，几十次调用），否则计分没有训练数据。

### 5.5 计分

对推文的每个 style flag `f`，用平滑计数：

```
score(f) = (down_f + α) / (down_f + up_f + 2α)   → 映射到 [-1, +1]
```

α = 1（拉普拉斯/Beta 平滑，防止「只出现过一次的属性」立刻笃定）。
推文的 C 分 = 各 flag 分数的加权聚合（建议取最负的那个 flag 主导，而非平均——**一条推只要
有一处明确的营销话术就该被记负，平均会把它稀释掉**，这正是 MIL 的直觉）。
无 flag 命中 = 通道弃权（abstain），不投 0 分——**弃权和「判断为中性」必须区分**，否则组合器
会把沉默当证据。

### 5.6 需要多少标注才谈得上有效

每个 flag 至少 ~20 条正负样本才有意义。按 `promo` 11 + `engagement_farming` 10 的现状，
最快见效的两个 flag 也还差一倍。**先上抽取、先攒数据，计分通道 default off。**

## 6. 通道 D：n-gram 贝叶斯（第二优先）

- 笔记的判断：C 是 D 的语义化版本，**未必都要**。但 `engagement_farming`（10 个踩）几乎是纯
  词面模式（「save this」「a thread 🧵」「1/」「你绝对不知道」），D 可能不必等 C 就有收益，
  而且**零 API 成本**。
- 实现：不建表。每轮判定前从 `x_tweets.text` 现算已标注推文的 token 计数，缓存在
  `VerdictManager` 里（几百条标注 = 毫秒级）。表化等到标注上千再说。
- 分词：中英混杂。latin 用 unigram + bigram（小写、去 URL/@/#），CJK 用字符 bigram。
  停用词表要小而明确——**别引 jieba 之类的重依赖**，本项目的依赖洁癖是选 sqlite-vec 的同一个
  理由（见主计划的选型对比表）。
- 计分：朴素贝叶斯对数几率，取 top-k 最有区分度的 token 求和，再挤压到 [-1, +1]；命中 token
  数低于阈值 = 弃权。`verdict_meta` 里存最有贡献的几个 token——**这是 D 相对 C 的最大优势：
  它能直接告诉你「因为这条推里有 "save this 🔖"」**。

## 7. 组合器与开关（2026-07-28 修订：投票制，废弃加权均值）

> **修订理由（两条，都在 §10.3 的回测之后确立）**：
> ① 加权均值被数据否决——各通道尺度不可比（C 的实际范围约 [-0.4, +0.1]，B/D 是
> [-1, +1]），均值把锐利的通道稀释掉：b+c+d 组合在 `pos>=0.25` 上 100%/7 次，
> 不如 B 单独的 100%/8 次，负向一次都不敢开口。
> ② 治理论证（用户决策，2026-07-28）：修订版 §9 的渐进路线以「通道的操作点」为
> 准入、监控归因、关停的单位——校准加权和把所有通道熔成一个混合分数，准入没有对象、
> 错误判定无法归因到通道、关停一个通道会改变其余通道的混合行为，恰好破坏
> 「每通道独立可关、独立可回测」这条笔记的核心要求。校准/逻辑回归 stack 是标注
> 上千之后的下一代组合器（届时组合器是被替换的层，通道接口不动），不是现在的候选。

- **组合器 = 投票**。每个通道先用**自己的阈值**独立分类
  （positive / neutral / negative / 弃权），合成规则四条：
  1. 任一通道判负（该通道负向已准入、且 `corroborated`），且无通道判正 → **negative**；
  2. 任一通道判正，且无通道判负 → **positive**；
  3. 冲突（有正有负）→ **neutral**——保守处理；冲突率由回测观察，「让正赢」留作
     数据支持后的改动；
  4. 全部弃权或全 neutral → **neutral**。
- 新增 `CONDENSER_VERDICT_CHANNELS=b`（逗号分隔，默认只有 b，**生产行为不变**）。
- **阈值按通道配置**：B 沿用 `positive_score` / `negative_score`；C / D 各有自己的
  `condenser_verdict_{c,d}_positive_score` / `_negative_score`（默认值 = 各自回测的操作点）。
- **负向双闸**：全局 `CONDENSER_VERDICT_NEGATIVE_ENABLED`（总闸 / kill-switch）+
  每通道 `condenser_verdict_{b,c,d}_negative_enabled`（修订版 §9 准入的对象，默认全 false）。
  两者同时为 true 该通道才可投负票。
- **连续分数不丢弃**：每通道的原始 score / confidence / 证据全部进
  `verdict_meta.channels`，给将来的逻辑回归 stack 和前瞻度量留数据。
- **既有闸门原样保留**：OOD、`min_neighbors`、不对称阈值、`min_down_neighbors`。
- **通道 B 的负样本过滤开关**：`CONDENSER_VERDICT_B_TOPIC_ONLY_NEGATIVES`（默认 false）。
  打开后 B 的负样本只取 `reason IS NULL OR reason='topic'`。今天打开只剩 4 个负样本
  （回测已验证：会退化成「全判正」的分类器，88% 精确度纯属基率），**等 `topic` 踩到 ~30 个
  再回测这个开关**。
- `verdict_meta` 升级：新增
  `{"channels": {"b": {...}, "c": {"flags": [["engagement_bait", -0.8]]}, "d": {"tokens": [...]}}}`。
  这是 UI 上「为什么」那一栏的数据源，web/iOS 的 `XVerdictDetail` 需要相应扩展。
  **必须纯增量**：顶层的 `score` / `neighbors`（通道 B 的证据）原样保留——已发布的
  iOS build 在解码它们，服务端先升级不能打空手机上的判定详情（forward thin-shell
  的同一个理由）。channels 块像 `META_NEIGHBOURS` 一样设上限（C 只存命中 flag +
  分数，D 只存 top 证据 token），每天写 ~1000 次的字段不倒中间状态。

## 8. 回测框架（先扩这个，再写通道）

**这是本计划里最先该做的事**：没有它，任何通道的取舍都是拍脑袋。

现有 `scripts/x_verdict_backtest.py` 只会：留一法 + 网格（正负阈值绑在一起）+ 只测 B。
`tmp/x_verdict_variants.py`（本次会话产出）已经补了：正负阈值解耦、按 reason 拆召回、
负样本集变体。**把后者合并进前者**，并加上：

- `--channels b,c,d` 选通道与组合权重；
- 每通道单独报告 + 组合报告（同一批 fold，可直接比较）；
- **弃权率**单列（一个总弃权的通道在「精确度」上永远好看）；
- **基率**打印在每张表旁边——这次判负失效正是靠「55.6% vs 49.2%」看出来的，没有基率对照
  就会把它当成「还行」；
- 读数顺序固定：coverage → negative precision → positive precision（脚本 docstring 已写明）。

跑法（**必须对生产库副本跑**，sweep 每折都会砸掉重建 KNN 索引）：

```bash
ssh -p 1122 root@<hh-hk-01> 'sqlite3 /opt/apps/condenser/data/condenser.db ".backup /tmp/snap.db"'
scp -P 1122 root@<hh-hk-01>:/tmp/snap.db tmp/prod-snapshot.db
CONDENSER_DB_PATH=tmp/prod-snapshot.db uv run python scripts/x_verdict_backtest.py --sweep
```

## 9. 判负上线的流程（2026-07-28 修订：准入门槛 + 前瞻验证，替代一次性关卡）

> **修订理由（用户决策）**：原文把重开判负写成一次性的回溯关卡，隐含「等所有证据
> 攒够、留出集齐备才许动」。但系统本就是渐进生效的设计（per-flag 的
> `min_observations` 门槛 + 训练集实时重算：一个 flag 的标注过线即自动开始投票，
> 无需任何代码或配置改动），验证也应当是**前瞻式**的：badge-only 的错误代价被刻意
> 压得很低（判错一个负徽标 = 用户多看一眼灰标签），而每天持续进来的新标注天然就是
> 「从不参与调参的留出集」——判定与标注都已归档（`x_feed_items.verdict` 不清除、
> `item_feedback` 实时），「先判后标」的推就是一次前瞻验证，事后随时可算精确度。
> 回溯留出集解决不了的选择偏差（§10.1 遗留问题 1），前瞻度量恰好解决。

**准入**（对象是「某通道的负向」这一档，不是全局，也不是单个 flag）：留一法回测中
该通道的负操作点同时满足以下四条，允许打开它的 `condenser_verdict_*_negative_enabled`
（同时打开全局总闸）：

1. negative precision **≥ 85%**，且
2. 负判定次数 **≥ 15**（样本量太小的高精确度没有意义），且
3. 该精确度**显著高于基率**（负样本占比），且
4. 错误的负判定里**没有一条是用户收藏过的**（这是最贵的错误类型）。

   > **2026-07-28 定义澄清**（原文写的是「点过赞或收藏」，在留一法里无法按字面满足：
   > 回测集全是标注过的样本，所以每个错误的负判定按定义就是一条点过赞的推，
   > 那样第 4 条等价于要求 100% 精确度、前三条全成多余）。**采用的读法：只禁收藏过的**
   > —— 收藏是权重 ×2 的强正样本，把它判负是最贵的错误；点过赞的误判由第 1~3 条的
   > 精确度门槛约束。回测脚本已自动检查这一条（`summarize` 只给同时满足
   > ≥85% / ≥15 次 / 零收藏误判的负操作点打星）。⚠️ 注意目前收藏数为 0，所以这条今天
   > 自动成立，它约束的是未来 —— 见 §13.2。

**前瞻验证**（准入之后持续进行，替代「攒回溯留出集」）：

- **只开徽标，不开折叠/隐藏**——「先攒信任再放权」是主计划的既有决策，本计划不推翻它。
  要开隐藏，另起一轮观察期并以前瞻数据为准再议。这条红线就是低代价试错的保证。
- 对「先有判定、后有标注」的推统计线上负精确度（数据都在库里，脚本即可起步，
  必要时进 `/api/x/status`）。已知的轻微反馈偏差：被打了负徽标的推可能更少被读到、
  标到——badge-only 且不改排序的前提下影响很小，但读数时要知道它存在。
- **关停条件**：某通道的线上负精确度跌破 85%，或出现一条收藏误判 → 关掉该通道的
  `*_negative_enabled`，回到回测。归因到通道正是投票制组合器（§7）保证的。

**覆盖自动扩大，无需再次人工准入**：已准入通道内部，新 flag 的标注过
`min_observations` 即自动参与打分（如 `engagement_farming` 到量后 C 的覆盖自然变宽）。
人工准入的颗粒度是「通道 × 负向」，flag 级的渐进是系统属性。

### 两处被真实数据推翻的设计

1. **「chip 指控不到就谁都不记账」是错的**。赞永远全额记到每个 flag（赞没有 chip，
   也不可能有），而踩只在 chip 对得上时才记 —— 于是 chip 够不着的 flag 只进不出。
   实测：`humblebrag` 在 **7 条踩过的推**上出现，却拿到 **+0.600** 的正分，
   模型学到了「凡尔赛是个好兆头」。改成**回退到分摊**（reader 确实讨厌了什么，
   只是他选的 chip 和抽取器的描述对不上）后变成 +0.043。
   注意 `topic`/`author` 仍然谁都不记账 —— 那是 reader 明说了「问题不在文风」。
2. **「薄证据叫得响」不是负向尾部不可靠的原因**。我一度这么写并据此加了收缩，
   然后用 `tmp/x_flag_drivers.py` 查了驱动 flag：全库最负的 5 条**全是赞过的 promo 推**
   —— 抽掉一条赞过的 promo 推，`promo_cta` 就只剩 4 条赞，比率恰好在「它判错的那一折」
   变得更负。这是留一法方差，任何打分规则都够不着，只有更多标注能解决。
   收缩**保留**了，但理由改成它真正成立的那条：`thread_bait`（3 次观测，-0.600）
   不该在同现时压过 `promo_cta`（18 次观测，-0.405）。

### chip 与抽取器的对齐度（这决定定向记账能不能落地）

| chip | 次数 | 抽取器在这些推上找到了对应 flag |
|---|---|---|
| `promo` | 11 | **11**（完美） |
| `engagement_farming` | 10 | 4（其余被读成 promo_cta / humblebrag） |
| `ai_slop` | 3 | **0**（被读成 promo_cta / emoji_spam / listicle） |

reader 说的「AI 味」和 qwen-flash 说的 `ai_slop` 基本不是一回事。这是 taxonomy 或
prompt 的下一轮工作，不是打分的问题。

### 给第 4 步（组合器）的前置发现

**各通道尺度不可比**：C 的实际取值范围约 [-0.4, +0.1]，B 和 D 是 [-1, +1]。
当前的加权均值组合因此把利的通道稀释掉了 —— 三通道组合（b=1/c=1/d=0.5）在 `pos>=0.25`
上是 100% / 7 次，**还不如 B 单独的 100% / 8 次**，负向则一次都不敢开口。
组合器要么先做每通道校准（把各自的分布拉到同一尺度），要么改用投票而不是取均值。

> **已解决（2026-07-28，步骤 4）**：选了**投票**。除了这里的尺度证据，还有一条治理理由
> 是校准制够不着的——修订版 §9 以「某通道的负向」为准入、归因、关停的单位，而混合分数
> 无法把一次错误判负归因到通道。校准 / 逻辑回归 stack 推迟到标注上千之后，届时组合器是
> 被替换的那一层，通道接口不动。详见 §7 与 §10.4。

|---|---|
| 通道 B 正向（线上真实徽标，`>=0.25`） | **0 / 2** —— 两次都判错。理由分别是 `topic` 和 `author` |
| 通道 B 负向影子 `<= -0.45` | 2 次判定，**两次都是收藏过的推**（§9 第 4 条的杀手条件） |
| 通道 B 负向影子 `<= -0.25` | 6 次判定，1 次对，**3 条收藏被判负** |

4 条收藏里有 3 条落在通道 B 的负向尾部（-0.456 / -0.469 / -0.326）—— 这不是阈值问题，
是纠缠缺陷的另一个方向：读者收藏的东西，在话题上离他踩过的东西很近
（邻居里 `@afuseai` / `@randyloop` 反复出现在两侧）。

### 结论

**步骤 5 的准入决策 = 不准入任何通道的负向**，`condenser_verdict_negative_enabled` 保持 false，
`CONDENSER_VERDICT_CHANNELS` 保持 `b`。理由不是「还差一点」，是「回测挑出来的那个操作点，
在多 17 条标注之后就不存在了，而唯一无选择偏差的前瞻样本给的分数更低」。

顺带发现的两件事，都写进 §13：

- **生产跑的是旧代码**（库里没有 `x_attributes` 表 ⇒ schema 仍是 v9），步骤 0–4 全部未部署。
  所以 C/D 在生产上**一个分数都没有**，影子回放对它们无话可说。
- 要拿 C/D 的前瞻证据，光部署还不够：`channels=b,c,d` 会让 C/D 的**正向**直接产生徽标
  （它们的正向精确度是 33% 和 64.7%，基率 48.7%），等于用读者的阅读体验换数据。
  缺的是一个「**只打分不投票**」的影子通道模式 —— 见 §13.6。

## 10.6 步骤 5b 实施记录（2026-07-28）：影子通道

§13.6 提的那条，当天就做了 —— 因为它是「继续攒证据」的唯一低成本路径。

`CONDENSER_VERDICT_SHADOW_CHANNELS`（逗号分隔，默认空）：列进来的通道**照常打分、
照常归档，但不投票**。落点三处：`verdict.shadow_channels()`（同时列在投票名单里的以投票
为准 —— 打错一个字母不该静默地把已准入的通道闭麦）、`_judge_one` 只把投票通道的分数
送进 `resolve`、`_meta` 给影子条目打 `{"verdict": null, "shadow": true}`。

**为什么需要 `shadow` 这个标记**：弃权的通道压根不在 `channels` 块里，所以没有标记的话，
「没资格说话」和「没什么可说」只能靠一个字段的缺席来区分 —— 那是给客户端埋雷。

一处必要的顺序修正：`'c' in keys` 的判断改成看**投票 + 影子**的并集。判定对一条推只发生
一次，属性晚到就永远不会被归档，影子测量会是一片空白。

其余保持不变：`algo` 仍按**投票**通道决定（`channels=b` + 影子 = `knn-v1`，因为判定确实
是 B 一个人做的），顶层 B 证据原样保留。web / iOS 的通道行各加一个「影子（不参与投票）」
标签（两端本来就把 `verdict` 解成可空，所以是纯增量）。

**真实端到端**（`tmp/x_shadow_e2e.py`，生产快照的可写副本 + 真 DashScope + 真 qwen-flash）：
同一个 48h 窗口判两遍，`channels=b` vs `channels=b` + `shadow=c,d` ——
**100 条判定，0 条判定改变，0 个顶层分数改变**；影子分数覆盖 C 23/100、D 64/100。
C 的覆盖率低是因为 `condenser_attr_batch=40`/轮，存量还没描述完，会自己涨上去。
371 后端 + 82 前端 + 174 Kit 测试绿。

**部署这一步需要的两个环境变量**（都不改判定行为）：
`CONDENSER_VERDICT_SHADOW_CHANNELS=c,d`，以及 `CONDENSER_ATTR_API_KEY`
（不设的话通道 C 连属性都没有；约 $0.01/天）。

## 10.7 步骤 6 实施记录（2026-07-29）：通道 A（作者先验）

计划把 A 排在最前又降级了它，理由是「29 个踩里只有 1 个 `author`」。这个判断把 **chip** 当成了
**信号**：作者先验不需要读者说「我讨厌这个人」，只需要读者一直对这个人的帖子说不。

### 推动它的实测：@IBKR

读者问「目前的算法能不能稳定识别 For You 里的 Interactive Brokers 广告」。查下来：归档里有
**14 条 @IBKR 推文，条条是广告，踩了 6 条**（全库被踩最多的账号，探针几乎每小时捞到一条），
而生产**把 14 条全判成了 `neutral`**。离线重算说明了为什么没有一个**文本**通道能接住：

| 通道 | 在这 14 条上的表现 |
|---|---|
| B 话题 | 6/14 `out_of_domain`（广告号会轮换题材——期货/外汇/黄金/石油/股票/利率，每换一次就是一片没有标注的邻域），判定当时**一条都没到过自己的阈值**（实时分 6 条 OOD + 7 条 -0.15~-0.44 + 1 条 -0.75） |
| C 属性 | 抽取器没跑到的就弃权 |
| D 词面 | 4/14 弃权（没有 token 过 `min_weight`） |
| **A 作者** | **14/14 命中，零弃权**，分数 -0.510~-0.562 |

**稳定性的量化对比**（这才是「能不能稳定识别」的答案）：A 对阈值 -0.25 有 **0.26 的余量**；
C 的余量只有 **0.046**，而 C 给同一条推文的分数**一天内漂移了 0.12**（0728 快照 -0.176 →
0729 快照 -0.296，即它是昨夜刚跨过自己的阈值的）。余量小于漂移的通道不叫稳定。

### 设计：Beta 平滑，不是硬规则

分析起手的硬规则是「≥2 踩且 0 正 → 判负」，留一法 92.9%/14 次、零收藏误伤。落地时改成 Beta
平滑（`ALPHA=1.0`、`CONFIDENCE_SMOOTH=2.0`，**故意低于通道 C 的 5.0**——一个作者被标注的次数
天然只有 2~6 次，k=5 会让被踩六次的账号仍然只算半票）。理由是硬规则中心有个悬崖：一个赞就
彻底赦免，第二个踩就彻底定罪。平滑保留排序、削掉两侧悬崖，而且是**可测量的**：硬规则唯一
判错的是 @yibie（3 踩 1 赞），平滑版给它 **-0.222，恰在阈值之上**，这个错在生产里根本不会发生。

不路由 chip（与 C 相反）：等一个账号被反复踩，chip 通常已经指向好几个不同属性，它们的共同点
就是「你一直对这个人说不」；只认 `author` chip 会丢掉建立信号的那 55 条踩。

### 回测（104 条真实标注，负样本基准率 53.8%）

| 阈值 | calls | 精确率 | 收藏误伤 |
|---|---|---|---|
| `neg <= -0.25` | 14 | **92.9%** | 0 |
| `neg <= -0.35` | 11 | 90.9% | 0 |
| `neg <= -0.45` | 6 | 100% | 0 |

**任何阈值下都没有收藏被判负**——这是别的通道都做不到的（b,c,d 投票误杀 5 条收藏）。但它离
§9 的 15 次仍差 1 次，且回测天然有选择偏差，所以 `condenser_verdict_a_negative_enabled`
默认 **false**，按 §10.6 的影子协议挣准入。

### 接线与验证

步骤 4 的契约原样复用：`CHANNEL_KEYS` 单一元组（能被 `channel_policy` 拿到却不在配置列表里的
通道不可能存在）、逐通道阈值、判负双闸门、`verdict_meta.channels` 增量。`db.x_pending_verdict_rows`
加了 `author_handle`；`_fit_channels` 复用 B 通道证据已经加载好的 handle 表，所以这个通道
**不花 API 调用、不加表、不加索引**。`prospective.shadow` 现在能**精确**回放 A 的 corroborated
（它的规则就是自己证据里的踩数，不像 B 的近邻数只存最近 5 个因而只是上界）。

生产快照副本上的端到端（真实 DashScope）：同一窗口 `channels=b` 对 `+shadow=a` ——
**100 条判定，0 条变化，0 个顶层分数变化**；A 在 100 条里对 9 条说话（91 条弃权是从没标注过的
作者，盲区如设计所料），其中 6 条正是 @IBKR 的 -0.5625，@yibie -0.222 在线上方。
399 后端 + 83 前端 + 175 Kit 通过，产物在 `tmp/2026-07-29-ib-check/`。

### 顺带被数据否掉的一个念头

「用通道 C 的 `promo_cta` 抓广告」看着可行（14 条里 13 条命中），但 `promo_cta` 在全库覆盖
104 条推文，其中 **7 条被赞、2 条被收藏**——读者赞的开源发布、产品推荐在 LLM 眼里同样是
`promo_cta`。读者讨厌的不是「推销」这个动作，而是「陌生商业品牌推销」。这是纠缠缺陷换了个
维度重演：C 分不开这两者，正如 B 分不开话题与文风。
