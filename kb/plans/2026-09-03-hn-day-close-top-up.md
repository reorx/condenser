# HN 准入：关账后补票（day-close top-up）

> 起因：2026-09-03 拿生产库的 `hn_stories` 和 hckrnews.com 的逐日存档做了一次
> 对比（§0），想知道我们的 HN 采集能不能当 hckrnews Top 20 的等效替代品。答案是
> Top 10 完全等效，Top 20 在 v14 的按速率放行下召回 93.8%、精确 90.5%，缺口全部
> 在第 18–32 名的边缘带。缺口的根因是 v14 的固有性质（§0.3），不是采集缺陷；本 plan
> 只补一个动作：**一天关账之后，把那天按最终分数应该在前 N 的、却没拿到名额的故事
> 补盖章，盖在它自己的 `first_seen_at` 上。** 其余（预算线、单向盖章、按判定日计数）
> 一律不动。

## 0. 证据

数据与脚本在本机 `tmp/2026-09-03-hn-vs-hckrnews/`（`tmp/` 不进库）：生产库只读导出
`hn_stories.json`（5044 行，07-14..09-02）、hckrnews `data/YYYYMMDD.js`
（07-12..08-31）、`compare.py`（逐日对比 → `report.md`）、`regimes.py`（分机制）、
`topup_sim.py`（本 plan 的模拟）、`boundary.py`（被否掉的边界方案）、`summary.md`。

### 0.1 hckrnews 的 Top N 到底是什么

从其前端 JS（`Day.pointsAbove`）读出的精确定义，脚本按此复现：

```
n     = ceil(当天条目时间跨度(小时) / 24 × N)      # 未成形的一天按比例缩 N
阈值  = 按 points 排第 n 名的分数
可见  = points >= 阈值                              # 并列一起显示；dead 默认隐藏
```

「天」= UTC 日，按首次上首页时间划分，与我们的 `hn_stories.day` 同口径。

### 0.2 对比结果（纯实时采集的 41 天，07-22..08-31）

| 指标 | 41 天 | v14 前 (07-22..08-13) | v14 后 = 现行 (08-14..08-31) |
|---|---|---|---|
| 首页故事存档覆盖率 | 96.4% (3970/4117) | 97.0% | 95.6% |
| Top 20 召回 | 96.7% (789/816) | 98.9% | **93.8%** (335/357) |
| Top 20 精确 | 94.7% (788/832) | 98.1% | **90.5%** |
| 放行条目落在 hck Top 30 内 | 99.2% | | |
| Top 10 召回 | 100% (410/410) | 100% | 100% |
| 每天放行数 | 20.3 | 20.1 | 20.5 |
| 分数快照 ours/hck 中位比 | 1.000 | | |

- 存档漏掉的 4%（144 条）全是低分：中位 18 分，最高 213，没有一条进过 hck Top 20。
  10 分钟采样 + 只看前 30 位看不到短暂上首页又被 flag 的故事。对等效性无影响。
- 我们有、hck 没有的 121 条里只有 2 条被放行，都是 hck 事后标 dead 并隐藏的大故事
  （704 / 672 分）。我们放行后不撤回，也不隐藏事后被 flag 的故事——已知差异，接受。
- v14 后 Top 20 漏掉 22 条：约 20 条「分数够 50、没有名额」（140–305 分），
  6 条跨天边界（hck 记 D、我们记 D+1，其中 5 条实际已放行），1 条 dead。
- 我们放行但 hck 排在 Top 20 之外的 47 条：39 条在第 21–32 名，6 条跨天边界。

### 0.3 根因：昨天的落选者抢今天的早班

每天约 62 条最终 ≥50 分，线只放 20 条，落选 42 条。第二天 00:10 线放出第一个名额时，
候选里昨天的落选者已是 300 分，今天的新故事只有十几分，按分数排序当然是昨天的赢。
实测 v14 后 198 条跨日盖章里，**只有 41 条（21%）是午夜前 4 小时首见的**，其余 79%
是前一天白天首见、分数已定型的落选者（最终分中位 302，87% 在 hck Top 20）。稳态是
每天 20 个名额约一半给昨天的落选者、一半给今天的；按存档日算每天仍有 20.5 条进时间线，
只是盖章晚一天。

这些落选者是好故事，第二天早上出现在时间线头部、读者看得见，**不该赶走**。所以：

- **不改计数口径**（§5.4a 按判定日计数）。改成按存档日会破掉「今天分组下的条目数 ≤
  budget(t)」这条不变量，还得每轮开两本账，且昨天的线在 23:59 已花光、落选者永远进
  不来——这正是 §5.4a 要避免的。
- **不挪预算日边界**（曾提议挪到 HN 最安静的 UTC 08:00）。只碰到那 21% 的爬分中故事，
  按「边界前 4 小时首见且最终 ≥50」的代理指标从 9.4/天降到 5.8/天，四成而已；对落选
  者机制零作用。撤回。

### 0.4 模拟：补票能买到什么

在 v14 后的 18 天上模拟（用最终分数，是上界；真实关账时分数略低）：

| 变体 | Top 20 召回 | 精确 | 每天放行 | 18 天新增 |
|---|---|---|---|---|
| 现状 | 93.6% (334/357) | 90.5% | 20.5 | 0 |
| V1 按存档日补满 N | 98.3% | 90.7% | 21.5 | 18 |
| **V2 补齐当天按分前 N** | **98.6%** | 90.7% | 21.6 | 19 |

补进来的正是那批「有分数、没名额」的故事，180–286 分，平均一天 1 条。精确率不变——
早放行的边缘故事仍在，所以是纯增量。剩下 5–6 条是跨天边界和 dead，补票治不了也不该治。
两个变体差 1 条；取 V2，语义更干净：**「当天按最终分数的前 N 一定在时间线上」**。

## 1. 决策（2026-09-03，用户拍板）

1. **只做补票，其余不动。** 预算线、单向盖章、48h 候选窗、按判定日计数全部保留。
2. **补票盖在故事自己的 `first_seen_at`。** 它落在存档日的分组下、读者游标后面：
   已滚过的读者在 All 视图看不到，`/timeline/new` 也不会报它；Unread 视图能看到。
   理由：日后回溯某天的 HN 信源时，这一天就是完整的前 N，比「盖在补票时刻、昨天的
   故事挂在今天」清晰得多。这正是 `stamp_history` 已有的路径（hckrnews 导入、v14
   回填都这么盖）。
3. **规则取 V2。** 不查配额计数：当天按最终分前 N 里没盖章的全部补上。直播盖章赢了
   名额但最终掉出前 N 的故事保留（单向），所以一天可以有 N + 几条。

## 2. 规则

对一个**已关账**的存档日 D（`hn_stories.day = D`）：

```
候选 = day = D AND qualified_at IS NULL AND is_dead = 0
       AND score >= min_score
       AND (peak_rank IS NULL OR peak_rank <= K)          # K=0 关
       AND day_rank <= N        # ROW_NUMBER() OVER (PARTITION BY day ORDER BY score DESC, id)
                                # half: day_rank*2 <= day_total+1；all: 不限
盖章   qualified_at = first_seen_at, qualified_rank = day_rank
```

这就是 `db.stamp_hn_history` 现有的谓词，**去掉它的配额计数**（`taken` /
`hn_qualified_count`）。那个计数按盖章日数：在 v14 的直播盖章下，D 日盖的章 = D 自己的
早班 + D−1 的落选者，通常已经是 N，补票会一条都补不上。去掉之后三个调用方（v14 迁移
回填、hckrnews 导入、本补票）是同一个动作：**把一个关账日对齐到它按分的前 N**。
hckrnews 导入的「不翻倍」性质仍然成立——谓词 `day_rank <= N` 本身最多命中 N 条，
现有用例 `test_topping_up_a_day_the_sampler_already_watched`（3 条直播 + 12 条导入 →
补 7）断言不变。

### 触发时机

每轮 `poll_once` 在 `_qualify()` 之后跑 `_top_up()`，对这两天各跑一次：

- **D−2：每轮都跑。** 它最晚首见的故事（23:59）的 48h 刷新窗到 D 日 23:59 才关，
  所以整个 D 日它的分数都还可能涨；D 日结束后分数冻结，不再需要 D−3。
- **D−1：`now.hour >= 12` 之后跑。** 让最晚首见的故事也刷够半天分。

盖章单向 ⇒ 幂等 ⇒ 每 10 分钟重复跑没有副作用，只是两个 SQL（窗口函数在 `day = ?`
子集上跑，5k 行的表毫秒级）。分数后来再涨进前 N 也能追上。

### 各面的后果

- **时间线**：补票故事出现在 D 日分组、按 `first_seen_at` 排在它本来的位置。
- **`/timeline/new`**：不报（它比 head cursor 旧）。这是有意的（§1.2）。
- **未读数**：+1（它是未读）。这是读者唯一的即时信号，也够了。
- **摘要管线**（`hn_summary`）：候选 SQL 没有年龄上限，补票故事自然成为候选并被摘要。
  每天约 1 条，可忽略的开销。
- **角标**：补票的 `qualified_rank` 是按分排名（day_rank），直播盖章的是名额序号，同一
  天里混用。接受；UI 文案不改。
- **`display_mode` 变更**：补票读 `stored_config()`，用的是**当前**模式。从 top10 切到
  top20 后，D−2 / D−1 会按 20 补齐——与「变宽从此刻起多放」的 §5.4c 精神一致，且只
  影响最近两天。

## 4. 测试（BDD，先写）

`tests/test_hn_admission.py` 新节「D: the day-close top-up」：

1. **关账日对齐到按分前 N**：D−1 有 3 条直播盖章（300 分）+ 12 条未盖章（200..189）
   + 1 条 40 分；`top_up(D 12:00)` 补 7；补的盖在各自 `first_seen_at`；`/timeline/days`
   里 D−1 计 10；40 分那条不进。
2. **补票落在原位、不在头部**：补票前取 head cursor，补票后 `/timeline/new` 报 0，
   而 `/timeline?date=D−1` 能看到它、未读数 +1。这是 §1.2 的合同。
3. **直播赢家掉出前 N 也保留**：D−1 一条直播盖章后分数跌到 30，另有 10 条 200 分未盖；
   补 10，该日共 11 条。
4. **幂等且追涨**：连跑两次第二次 0；随后一条分数更新挤进前 N，再跑补 1。
5. **触发时机**：`top_up_days(D 08:00) == [D−2]`，`top_up_days(D 12:00) == [D−2, D−1]`。
6. **feed 未启用不补**：`update_hn_subscription(enabled=False)` 后 `top_up` 返回 0
   （`stamp_history` 自己仍能盖，那是导入/迁移的路径）。

`tests/test_hn.py`：

7. **轮次里跑补票**：`make_manager` + 固定 `now`（12:00），D−1 一条 200 分未盖章，
   `poll_once` 后它有 `qualified_at == first_seen_at`。

回归：`test_topping_up_a_day_the_sampler_already_watched` 断言不变（说明见 §2）。
